Before architecture-affecting work, read every current-state page relevant to the affected packages and `AGENTS/ARCHITECTURE/TARGET_WORKFLOW.md`. Target documentation is approved direction, not evidence that its code exists.

## Commands
- Run everything: `npm run dev` (server ws+http on localhost:3001, client http://localhost:5173, agent)
- Typecheck: `npm run typecheck` (all packages) or `npx tsc --noEmit -p packages/<name>`
- Tests: `npm test` (all packages) — server suite holds invariants T1-T12 + pressure + hardening; client uses vitest, the rest node:test
- Client build: `npm run build -w @workspace/client`
- Env overrides: `PORT`, `CORS_ORIGIN`, `DATA_DIR`, `GOOGLE_AUTH_ENABLED`, `EMAIL_AUTH`, `AGENT_TOKEN`, `CLIENT_DIST`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_URL`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GIT_CREDENTIAL_ENCRYPTION_KEY`, `GITHUB_REDIRECT_URI` (server), `WS_URL`, `AGENT_TOKEN`, `AGENT_PROVIDER`, `CLAUDE_WORKDIR`, `GEMINI_API_KEY`, `AGENT_NAME`, `AGENT_MODEL` (agent), `VITE_WS_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` (client). Full table in `AGENTS/DEPLOY.md`.
- One `.env` at the repo root (see `.env.example`) feeds `npm run dev` for all three processes: server/agent `config.ts` load it explicitly via `dotenv.config({ path: <repo root>/.env })` (npm workspaces run scripts with cwd = the package dir, so a bare `dotenv.config()` misses it), and `packages/client/vite.config.ts` sets `envDir` to the repo root so `VITE_*` vars resolve the same way. Docker Compose doesn't need any of this — it injects `.env` as real container env vars.
- Local dev DB (for networks that block outbound 5432): `npm run dev:db` starts an embedded Postgres 17 in `data/dev-db/`, applies `supabase/migrations/*.sql`, then point `SUPABASE_DB_URL` at `postgresql://postgres:postgres@localhost:55432/postgres`.
- Deploy: `AGENTS/DEPLOY.md` — one origin in production (server serves the built client), Dockerfile/compose at root.

## Architecture invariants
- Supabase-managed Postgres is the workspace store (workspaces, memberships, actors, chat/board/context/agent-work records, projects, Toolman nodes/mounts/executions, actor-owned GitHub connections, workspace-linked Git repositories and branch-channel bindings). Schema lives in `supabase/migrations/*.sql`; `packages/server/src/db.ts` (`WorkspaceDb`, postgres.js) only connects and queries — it never creates tables. Every table has RLS enabled with no policies (deny-all through Supabase's PostgREST Data API — the app never uses it; the server connects directly as the table-owning `postgres` role, which RLS does not restrict).
- Toolman authorization is the agent mutation boundary: `authorizeMutation` in `packages/server/src/board/Toolman.ts` requires either a workable owned ticket or an explicit bounded chat grant, applies project binding and path scope where knowable, and treats unknown tools as mutating (fail closed). Project actions execute only after this decision, through either a paired Toolman node or the managed Git checkout service. Do not add agent write paths that bypass it. Claude-backed agents enable only read-only native tools — `ClaudeBrain` by restricting the tool list, the ACP runner by denying any tool call that is not a read, search, think or fetch — so native provider tools cannot mutate around the boundary.
- Tickets must declare `scopePaths` (400 SCOPE_REQUIRED otherwise); an entry ending in `/` grants a subtree, anything else exactly that file. Tickets also require an accepted plan, why/effect, and later human approval with owner, criteria and impact map.
- Item statuses: proposed → approved/denied; approved → in_progress → blocked/done; done → approved (reopen). Every ticket starts proposed, including human-created ones. Humans approve/deny/edit/delete over the HTTP API (`/api/board/items`, `/api/board/plans`, plus `/api/actors` and `/api/board/items/:id/events`); agents propose plans and tickets. I1/I2 assertions live in `BoardService` and are tested — never trust actor identity from a request body.
- Every board mutation writes exactly one `board_events` row in the same transaction and fans out a `{channel:"board", type:"item.*"}` envelope on the websocket.
- Auth is Supabase Auth (Google OAuth and/or email+password), entirely client-side via `@supabase/supabase-js`. A human's `actors.id` is their Supabase Auth user id; `actors` is global identity, while `workspace_members` records independent `owner` or `member` membership in any number of workspaces. The first username claim—manual or from `desired_username` metadata—creates `{username}'s workspace` with that human as owner. `GET /api/account` returns memberships and access requests; zero memberships remains valid after leaving, and a pending invite flow takes precedence over automatically opening a sole membership.
- Sign-in gating: `GOOGLE_AUTH_ENABLED=1` and/or `EMAIL_AUTH=1` only control which options the client offers (the providers themselves are configured in the Supabase dashboard). Both unset = the running server refuses every join and the client shows a "contact hello@convyio.com" dead end instead of a login screen. Guest-name joins (no gate at all) only happen in tests that build a `Hub` directly without `authorizeJoin`.
- Joining is workspace-scoped. Humans connect to `/ws/:workspaceId` with a Supabase access token; the server verifies both identity and current membership. Each `welcome` frame mints an in-memory 12-hour HTTP bearer token bound to that actor and workspace. Switching workspaces closes and unmounts the old workspace session before opening another. Paired agent and Toolman credentials resolve their workspace server-side and receive workspace-specific websocket URLs.
- Every workspace is created with a workspace-scoped managed noodle actor and membership, durable owner/noodle join notices, and three one-time welcome messages. `AGENT_TOKEN` resolves only the stored noodle actor while that membership is active; removing noodle prevents automatic rejoin, while owner-only restore re-adds the same actor without replaying its join notice or welcomes.
- Workspace owners create and revoke single-use seven-day invite links, approve or deny access requests, change human roles and remove members. The last owner cannot demote themselves or leave. Removing membership preserves the global actor and historical attribution.
- CORS: locked to `CORS_ORIGIN`; the dev default `localhost-dev` mirrors any localhost/private-LAN origin (Vite may land on 5174+). Production is single-origin so CORS barely matters there.
- A project is the shared resource; a Toolman node is only the transport to one concrete local mount. Agents can discover projects and request access, but only the project owner assigns/revokes agents, resolves requests or changes `ask`/`always`/`deny`. `ask` prompts the online owner once per agent conversation and that approval avoids a duplicate mode prompt; `always` is durable folder consent while the node remains available but does not bypass the conversation permission mode; `deny` always refuses.
- Toolman pairing and installation credentials resolve their workspace server-side. Re-pairing or reconnecting one node evicts its older socket, revocation disconnects it immediately, and a node disconnect fails its in-flight executions. Paired nodes, opaque mounts, assignments and execution records are workspace-scoped; concrete local paths remain only on the node.
- GitHub connections are global human-owned OAuth credentials encrypted with AES-256-GCM; expiring access tokens rotate through encrypted refresh tokens and disconnect erases both ciphertexts. Linked repositories are workspace-scoped Git projects with managed checkouts under `data/workspaces/<sha256(workspace-id)>/repositories/`. Human forge APIs recheck workspace membership; agents use project assignment, owner consent and the Toolman boundary instead of receiving provider credentials.
- Managed Git transport accepts only credential-free `https://github.com/…` repository URLs, disables repository hooks and credential helpers for authenticated transport, and targets the stored provider URL rather than mutable local `origin`. Managed checkouts expose first-class status/fetch/pull/push/branch/commit actions; arbitrary project shell commands require a paired local Toolman checkout. Creating a non-default branch creates a linked chat channel, and deleting the branch or merging its pull request archives that channel.
- Agent presence semantics: green=working, orange=idle, red=blocked on a human, grey=offline. Approved ticket work is queued by the server on `agent_run_requests` and claimed after reconnect. Registered members (humans and agents) persist in the roster when offline (grey) and stay @-mentionable; demo personas and guest actors are not members and drop out.
- The client composes per-domain hooks under a `WorkspaceContext`; components take workspace data/actions from context and navigation callbacks as props. Board ops are optimistic with rollback; failures surface as toasts.
- Scripted demos: JSON scripts in `packages/server/assets/demo/scripts/` (schema in `src/demo/script.ts`), played by `DemoOrchestrator` through the real hub/board pipeline. There is no client-side demo fallback — demos need a running server and agent. Seed fixtures live in `assets/demo/seed/`.

## Testing against Supabase
- Server tests create a throwaway Postgres schema per suite (`packages/server/test/pgSchema.ts`), apply every migration into it, and drop it after — they need a real `SUPABASE_DB_URL`.
- Production runs on Railway (project `convyio`): the **shell** service (`@workspace/server`, Dockerfile build, start command `node_modules/.bin/tsx packages/server/src/index.ts`, custom domain `app.convyio.com`) serves the built client + API + ws; **noodle** (`@workspace/agent`) is a separate hosted managed-agent service. With `AGENT_TOKEN`, it polls `/api/hosted-agent/workspaces` and keeps one Gemini runner connection plus an isolated data directory per enabled workspace. The shell never hosts provider execution. User-created agents are the user's software (Block/goose model). The leftover `@workspace/client` Railway service is bogus and should stay deleted. `VITE_SUPABASE_*` reach the browser bundle via Dockerfile build ARGs.
- `SUPABASE_DB_URL` in `.env` points to the Supavisor session pooler (`*.pooler.supabase.com:5432`). Running many server test files concurrently can hit `EMAXPOOLSREACHED` or `CONNECTION_ENDED` errors from the pooler. Use a local Postgres or the Supabase transaction pooler (port 6543) for heavy test runs if possible.
