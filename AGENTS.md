## Commands
- Run everything: `npm run dev` (server ws+http on localhost:3001, client http://localhost:5173, agent)
- Typecheck: `npm run typecheck` (all packages) or `npx tsc --noEmit -p packages/<name>`
- Tests: `npm test` (all packages) — server suite holds invariants T1-T12 + pressure + hardening; client uses vitest, the rest node:test
- Client build: `npm run build -w @workspace/client`
- Env overrides: `PORT`, `CORS_ORIGIN`, `DATA_DIR`, `GOOGLE_AUTH_ENABLED`, `EMAIL_AUTH`, `AGENT_TOKEN`, `CLIENT_DIST`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_URL` (server), `WS_URL`, `AGENT_TOKEN`, `AGENT_PROVIDER`, `CLAUDE_WORKDIR`, `GEMINI_API_KEY`, `AGENT_NAME`, `AGENT_MODEL` (agent), `VITE_WS_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` (client). Full table in `AGENTS/DEPLOY.md`.
- One `.env` at the repo root (see `.env.example`) feeds `npm run dev` for all three processes: server/agent `config.ts` load it explicitly via `dotenv.config({ path: <repo root>/.env })` (npm workspaces run scripts with cwd = the package dir, so a bare `dotenv.config()` misses it), and `packages/client/vite.config.ts` sets `envDir` to the repo root so `VITE_*` vars resolve the same way. Docker Compose doesn't need any of this — it injects `.env` as real container env vars.
- Deploy: `AGENTS/DEPLOY.md` — one origin in production (server serves the built client), Dockerfile/compose at root.

## Architecture invariants
- Supabase-managed Postgres is the workspace store (workspaces, workspace_members, actors, messages, board_items, append-only board_events, channels, attachments metadata, agent_invites). Schema lives in `supabase/migrations/*.sql`; `packages/server/src/db.ts` (`WorkspaceDb`, postgres.js) only connects and queries — it never creates tables. Every table has RLS enabled with no policies (deny-all through Supabase's PostgREST Data API — the app never uses it; the server connects directly as the table-owning `postgres` role, which RLS does not restrict).
- The board is a permission boundary: `authorizeMutation` in `packages/server/src/board/Toolman.ts` refuses any mutating agent action without a workable (approved/in_progress) board item whose `scope_paths` cover the target path. Tools not known read-only are treated as mutating (fail closed). Do not add agent write paths that bypass it. Known exception: with `AGENT_PROVIDER=claude`, `ClaudeBrain` leaves Claude Code's native Bash/Write/Edit tools enabled ungated — an accepted MVP gap recorded in `AGENTS/ARCHITECTURE.md`'s 2026-08-09 decision log, not a precedent for new bypasses.
- Agent proposals must declare `scopePaths` (400 SCOPE_REQUIRED otherwise); an entry ending in `/` grants a subtree, anything else exactly that file. Human items may omit scope (explicit unrestricted grant); humans can narrow/widen scope via PATCH.
- Item statuses: proposed → approved/denied; approved → in_progress → blocked/done; done → approved (reopen). Humans create (auto-approved) and approve/deny/edit/delete over the HTTP API (`/api/board/items`, plus `/api/actors` and `/api/board/items/:id/events`); agents only propose. I1/I2 assertions live in `BoardService` and are tested — never trust actor identity from a request body.
- Every board mutation writes exactly one `board_events` row in the same transaction and fans out a `{channel:"board", type:"item.*"}` envelope on the websocket.
- Auth is Supabase Auth (Google OAuth and/or email+password), entirely client-side via `@supabase/supabase-js` — the server never sees a password or Google credential, only the resulting Supabase JWT, which it re-verifies with the Supabase admin client on every call (`Auth` in `packages/server/src/auth/`). A human's `actors.id` is their Supabase Auth user id. `actors` is global identity; registration into the single workspace (named `test_space`) is a separate `workspace_members` row written at signup. First sign-in binds a permanent username via `POST /api/auth/username`; `GET /api/auth/session` reports ok/needs_username; `GET /api/auth/config` tells the client which sign-in methods to show.
- Sign-in gating: `GOOGLE_AUTH_ENABLED=1` and/or `EMAIL_AUTH=1` only control which options the client offers (the providers themselves are configured in the Supabase dashboard). Both unset = the running server refuses every join and the client shows a "contact hello@convyio.com" dead end instead of a login screen. Guest-name joins (no gate at all) only happen in tests that build a `Hub` directly without `authorizeJoin`.
- Joining: humans present their Supabase access token in the ws `join`; client-supplied names are ignored for humans (I1). Agents present either the server-wide `AGENT_TOKEN` or a user-created per-agent invite token (`POST /api/agents`, humans only; revoking via `DELETE /api/agents/:id` evicts the agent). The `welcome` frame carries a short-lived HTTP bearer token (in-memory, 12h TTL, revoked when the participant's last connection closes) + apiUrl, plus the channel list and the workspace identity (`{id, name}`).
- CORS: locked to `CORS_ORIGIN`; the dev default `localhost-dev` mirrors any localhost/private-LAN origin (Vite may land on 5174+). Production is single-origin so CORS barely matters there.
- Toolman file actions are sandboxed to `data/workspace/`.
- Agent presence semantics: green=working, orange=idle, red=blocked on a human, grey=offline. Agent restart recovery: pending proposal work is persisted (`data/agents/<name>/pending-work.json`) and swept against the board snapshot on rejoin. Registered members (humans and agents) persist in the roster when offline (grey) and stay @-mentionable; demo personas and guest actors are not members and drop out.
- The client composes per-domain hooks under a `WorkspaceContext`; components take workspace data/actions from context and navigation callbacks as props. Board ops are optimistic with rollback; failures surface as toasts.
- Scripted demos: JSON scripts in `packages/server/assets/demo/scripts/` (schema in `src/demo/script.ts`), played by `DemoOrchestrator` through the real hub/board pipeline. There is no client-side demo fallback — demos need a running server and agent. Seed fixtures live in `assets/demo/seed/`.

## Testing against Supabase
- Server tests create a throwaway Postgres schema per suite (`packages/server/test/pgSchema.ts`), apply every migration into it, and drop it after — they need a real `SUPABASE_DB_URL`.
- Production runs on Railway (project `convyio`): the **shell** service (`@workspace/server`, Dockerfile build, start command `node_modules/.bin/tsx packages/server/src/index.ts`, custom domain `app.convyio.com`) serves the built client + API + ws; **noodle** (`@workspace/agent`) is a separate demo-agent service running only `packages/agent`, joining over the public `wss://` URL with `AGENT_TOKEN` like any outside client. Agents are the user's software (Block/goose model) — never host them inside the shell. The leftover `@workspace/client` Railway service is bogus (the client is static files, not a process) and should stay deleted. `VITE_SUPABASE_*` reach the browser bundle via Dockerfile build ARGs (Railway forwards service variables only for declared ARGs).
- `SUPABASE_DB_URL` in `.env` points to the Supavisor session pooler (`*.pooler.supabase.com:5432`). Running many server test files concurrently can hit `EMAXPOOLSREACHED` or `CONNECTION_ENDED` errors from the pooler. Use a local Postgres or the Supabase transaction pooler (port 6543) for heavy test runs if possible.
