CONVYIO DIFFERENTIATED ONBOARDING SPECIFICATION

Status: canonical onboarding direction
Aligned with: AGENTS/PRODUCT_DIRECTION.md
Prepared: 2026-08-19

PURPOSE

Convyio onboarding must prevent the two most likely incorrect mental models:

- Slack or Discord with bots;
- a generic multi-agent orchestration or swarm program.

The experience must establish a different system of work:

- conversation is the canonical work surface;
- shared context changes the plan before execution;
- responsibility and authority become explicit;
- agent work remains visible;
- the result returns to the same thread with evidence;
- other planes are projections or resource controls, not disconnected products.

A generic noodle response is not differentiated activation. The onboarding succeeds when a selected ICP user understands and begins the shared, governed work loop.


1. FIVE-MINUTE STANDARD

Within five minutes, a correctly selected user should be able to explain Convyio in language equivalent to:

    Convyio is where our team turns shared context into approved agent work and gets back a result we can review.

The following explanations indicate failure:

- Slack with a bot.
- Another coding agent.
- A multi-agent framework.
- A swarm dashboard.
- A chat app with a Board tab.
- A project-management system with AI.

The standard is comprehension and felt differentiation, not universal subjective affection. Product, message, audience and proof should be refined until nearly every correctly selected ICP participant reaches the right mental model quickly.


2. AUDIENCE

Primary wedge:

    A 2–10 person technical team running several independently owned coding agents against the same product under deadline.

The first user may arrive alone. Do not require an invite, GitHub connection, local-folder pairing or user-owned agent before first value.

Strong initial jobs:

- investigate a bug before anyone changes code;
- turn a feature idea into a plan the team can trust;
- untangle a change that keeps returning from review;
- coordinate a release, hotfix or client delivery across mixed agent tooling.

The first-run path should infer intent from the work the user chooses instead of adding a persona questionnaire.


3. ONBOARDING ARCHITECTURE

The complete system has four layers:

1. Canonical demo/video: establish the category and prove the full loop.
2. Real-work activation: apply the first half of the loop to the user's work.
3. Persistent getting-started guide: continue into projects, local agents and teammates.
4. Contextual guidance: explain unfamiliar decisions at the moment they occur.

The demo and real-work activation are distinct:

- The demo guarantees comprehension without setup or model latency.
- The real-work path proves that Convyio is useful beyond a scripted example.

Both use the same product language and visual artifacts.


4. FIRST EXPERIENCE: THE CANONICAL DEMO PLAYS FIRST

The first visual onboarding experience is a short, polished demo of the differentiated loop.

It appears over the connected starter workspace after the welcome frame is ready. The user may skip immediately and begin using the product.

The demo should be the same canonical story used on the landing page. The app onboarding implementation is its source of truth.

The in-app walkthrough starts directly inside the real Convyio interface. Its opening frame says:

    See Convyio in one shared conversation.

    Follow two founders and their agents from shared evidence to a reviewed Plan, authorized implementation, and a result with proof.

The before/after workflow comparison belongs to the landing-page or explanatory video, not the interactive product walkthrough.


5. CANONICAL CROSS-REPO API SCENARIO

The canonical product story is a cross-repo API compatibility change involving two founders and their independently owned agents.

Scenario:

1. Maya asks @noodle to review changing the backend project API from `owner_name` to `owner`.
2. Noodle confirms the server can add `owner`, but has not checked every consumer.
3. Tom asks @hermes to inspect the independently owned web and mobile clients.
4. Hermes finds that both still use `owner_name` and that mobile cannot update during this release.
5. Maya asks Noodle to build on Hermes's finding.
6. Noodle proposes a safe rollout: add `owner`, preserve `owner_name` for one release, update web, leave mobile unchanged and contract-test both fields.
7. Noodle produces one inline PlanCard from the backend and client findings.
8. Hermes adds the client constraint: mobile must remain unchanged and `owner_name` must keep working.
9. The Plan visibly changes before execution.
10. The viewer accepts the Plan and approves one bounded Ticket with an explicit owner, file scope and contract check.
11. Noodle updates the API response and web client.
12. A ResultCard proves that new and existing clients continue working and that mobile stayed unchanged.

Core captions:

    The backend view is only part of the picture.

    Two owners. Two agents. One shared Plan.

    The client constraint changed the Plan before execution.

    Same agents. Different system of work.

Agent mentions demonstrate shared reasoning and make each contribution legible. They do not replace structured responsibility: executable work still requires one explicit Ticket owner and human-approved authority.

The fixture demonstrates why separately owned backend and client context must meet before implementation. Neither agent has enough context alone.

The demo must not auto-approve on behalf of the viewer. The user must make at least one consequential decision.

If the landing-page version must remain passive, visibly animate the viewer's decision but label the demo as a product walkthrough. The in-app version makes the decision interactive.


6. DEMO VIDEO STORYBOARD

Suggested narrative spine:

    Shared request -> backend finding -> client finding -> cross-agent synthesis -> compatibility constraint -> changed Plan -> human acceptance -> bounded implementation -> contract evidence

Show the old workflow contrast in the video, then enter the real Convyio thread. Keep the interactive walkthrough focused on the product itself.

During the walkthrough:

- spotlight Maya's request;
- spotlight Noodle's backend finding;
- pause on the partial-context checkpoint;
- spotlight Tom asking Hermes and Hermes's client finding;
- spotlight Noodle building on Hermes's result;
- spotlight the combined PlanCard;
- spotlight the compatibility constraint and Changed before execution;
- wait for the real Accept action;
- spotlight the bounded Ticket and wait for the real Approve action;
- spotlight the ResultCard showing both contract fields and unchanged mobile behavior.

Close on:

    Same agents. Different system of work.

    Convyio keeps the conversation, the decision, the work and the proof in one thread.

The interactive walkthrough uses readable message pacing and explicit Continue controls between major chapters. Everything outside the current target is blanked so one message or artifact is clear at a time. Short landing and social cuts may compress the same sequence, but they must preserve the two-owner/two-agent causal story. Clarity outranks a fixed runtime.


7. DEMO ACCESSIBILITY AND PLAYBACK

- No autoplay audio.
- Provide captions/transcript.
- Provide pause, replay and skip.
- Respect prefers-reduced-motion.
- Reduced-motion users receive a concise poster/storyboard with the same causal sequence.
- The first frame must explain what will be learned.
- Do not force the user to wait for playback before entering the product.
- Focus must move into modal playback and return correctly on close.
- The demo must work at narrow viewport widths and 200% zoom.
- The demo must not claim behavior absent from current architecture.


8. TRANSITION FROM DEMO TO REAL WORK

After the demo:

    Now use the first half of that loop on something real.

Primary action:

    Bring one piece of work

Secondary actions:

    Replay the example
    Explore on my own

Do not ask the user to create channels, configure a Board, connect GitHub, add an agent or invite a teammate yet.


9. REAL-WORK STARTERS

Offer job-based starters:

- Investigate a bug before anyone changes code.
- Turn a feature idea into a scoped plan.
- Untangle a change that keeps returning from review.
- Describe something I am working on.

Each option prefills the real composer with an editable @noodle request.

Example: investigate before coding

    @noodle Help me investigate this before anyone changes code: [describe the problem]. Surface the assumptions, constraints and missing context, then propose a plan. Do not modify anything.

Example: scope a feature

    @noodle Turn this feature idea into a plan the team can review: [describe the idea]. Separate assumptions from known constraints and ask one important question before proposing work.

Example: recurring review rework

    @noodle Help me understand why this work keeps coming back from review: [describe it]. Identify the constraint we are discovering too late and propose a safer plan.


10. WORK BRIEF / PLANCARD

The first useful output should be a structured inline PlanCard, not only prose.

The PlanCard should show:

- intended outcome;
- context that matters;
- assumptions;
- constraints;
- open question;
- proposed approach;
- acceptance criteria;
- likely affected resource;
- proposed owner;
- changes caused by later information.

The card uses the existing canonical Plan record. `Work Brief` may be user-facing language for a concise Plan, not a second data model.

Inline actions:

- Add constraint.
- Answer question.
- Edit/refine.
- Accept.
- Request changes.
- Discuss.
- Open Board view.

A Plan created in conversation remains in that thread. Board is another view of the same entity.


11. SOLO MULTIPLAYER MOMENT

Before Plan acceptance, noodle asks:

    What is one thing a reviewer, PM, customer or security owner would not let this work break?

The user adds or confirms one meaningful constraint.

The Plan shows the consequence:

    Changed before execution

This gives the solo champion the multiplayer insight without pretending another person is present.

Afterward explain:

    This is where another tool usually discovers the constraint during review. In Convyio, the person who owns it can add it before the work starts.

Do not force an invite.


12. CONTROL WITHOUT BUREAUCRACY

Translate internal authority concepts into human questions:

- Who owns this?
- Which project or folder does it apply to?
- What may change?
- What must remain true?
- How will we know it is done?

Do not initially teach:

- scope_paths;
- action capability maps;
- impact-map implementation details;
- permission-mode architecture;
- event-envelope terminology.

Show that quick read-only asks remain quick. Consequential work gains structure because it changes the world.

The intended feeling is confidence and momentum, not compliance administration.


13. EXECUTION AND ORCHESTRATION

Show orchestration as a work progression:

    Understanding -> Planning -> Waiting for you -> Assigned -> Working -> Verified

When relevant, show:

- the approved owner;
- the project/resource;
- current state;
- the human decision needed;
- what happens next.

Do not show swarm topology, agent graphs or manager/worker jargon.

The onboarding must not imply autonomous agent-to-agent delegation. Convyio coordinates responsibility, authority, project access, durable dispatch and return of results.


14. RESULTCARD

The execution loop ends with a coherent ResultCard in the origin thread.

Required content:

- requested outcome;
- concise result;
- what changed;
- what deliberately did not change;
- files/artifacts/branch/pull request;
- checks and verification;
- acceptance-criteria result;
- human decisions that affected the run;
- next recommended action;
- links to Plan, Ticket, trace, logs and project view.

Raw traces and ToolCards remain inspectable evidence. They are not the primary product output.

The onboarding should explicitly point to ResultCard as the practical thing Convyio produces.


15. MULTIPLAYER EXPANSION

After the ResultCard:

    This is the moment another person normally enters in review.
    Bring them into the next one before the work begins.

Primary contextual action:

    Invite the person who usually catches this

Equal secondary action:

    Keep working solo

The user can continue without inviting anyone.


16. AGENT AND PROJECT EXPANSION

Only after differentiated value:

- connect a GitHub repository;
- share a selected local folder;
- pair an existing local agent;
- add another independently owned runtime;
- invite teammates;
- explore Board, Projects and Resources projections.

Message:

    Use the agents your team already runs. Their credentials remain with their owners; Convyio carries the shared mission and authority.

Do not make setup completion the onboarding goal.


17. VISUAL ONBOARDING LAYER

The first product demo is the main visual education. The interactive walkthrough begins in the real product rather than replaying the video's before/after explanation.

During playback, a semantic spotlight dims unrelated UI and highlights the current message, Plan field, decision control, Ticket, ResultCard or composer. The persistent bottom guide explains the current significance. At chapter boundaries, the product dims completely and the guide becomes the primary focus.

The bottom guide has three modes:

- compact caption while a product target is highlighted;
- chapter checkpoint with an explicit Continue action;
- action prompt that waits for the real Accept or Approve control rather than bypassing it.

Spotlight behavior:

- scroll the semantic target into view without changing document layout;
- leave the highlighted target clickable while blocking pointer interaction outside it;
- keep the bottom guide above the dim layer;
- constrain keyboard focus to the guide and highlighted controls;
- Escape pauses;
- provide explicit pause, skip and replay;
- respect reduced motion by moving the spotlight without animated transitions;
- fall back to an unanchored guide if a target is unavailable.

Stable targets use semantic data attributes rather than styling selectors. Current targets are:

- canonical conversation;
- individual demo messages;
- inline PlanCard;
- Changed before execution;
- real Plan acceptance;
- bounded Ticket;
- real Ticket approval;
- ResultCard;
- real composer for Bring one piece of work.

Do not tour all navigation tabs.


18. PERSISTENT GETTING-STARTED GUIDE

The guide should track outcomes, not visited features.

Suggested milestones:

1. Turn real context into an accepted Plan.
2. Add or confirm a meaningful constraint.
3. Approve bounded work and inspect the ResultCard.
4. Connect a real repository/folder or pair a user-owned agent.
5. Invite a teammate or add another independently owned agent.

The first three define the differentiated product loop. The last two deepen fidelity and multiplayer value.

The guide is dismissible, replayable and non-blocking. It is available from a quiet Getting started control or mascot entry point.


19. CONTEXTUAL GUIDANCE

First PlanCard:

    This is the shared understanding the work will use.

First added constraint:

    This changed the plan before execution.

First proposed Ticket:

    You are approving who acts, where, what may change and how the result will be checked.

First permission request:

    The agent reached a human checkpoint. This decision stays attached to the work.

First ResultCard:

    This is the reviewable outcome. Open the trace only when you need the full evidence.

First Board visit:

    Board is another view of the work already living in your conversations.

First Projects visit:

    Projects groups the same work and results by repository.

First Resources visit:

    Share only the folder you choose. Its owner controls which agent may use it.

First Add Agent visit:

    Pair the agent runtime you already trust. Provider credentials stay with its owner.

First invite:

    Invite the person whose context should affect the work before execution.


20. FIRST-RUN STATE

Use durable account-scoped onboarding state rather than a browser-only completion flag.

State must identify:

- actor;
- starter workspace;
- onboarding version;
- pending, in_progress, paused, completed or skipped status;
- current stage;
- selected real-work intent;
- started, demo-viewed, Plan-produced, Plan-accepted and finished timestamps.

Existing users are not automatically forced through first-signup onboarding. The complete demo and guide remain manually replayable.

Invite continuation takes precedence. First-signup onboarding appears only in its bound starter workspace.

Server state is authoritative; a small browser cache may suppress duplicate tabs and avoid flicker.


21. FAILURE AND RECOVERY

Noodle offline:

- The deterministic demo still establishes the product.
- The real-work step remains resumable.
- Do not fake a live response.

Noodle slow:

- Let the user continue while noodle works.
- Keep the result attached to the original request.

No project connected:

- Complete the Plan/constraint/acceptance path.
- Offer the canonical example for the full execution proof.
- Defer project setup.

Noodle removed:

- Explain that the built-in guide is unavailable.
- Offer owner restore or pair-an-agent later.
- Do not dead-end product access.

Workspace switch:

- Pause and unmount onboarding.
- Never carry drafts or progress into another workspace.

Target missing:

- Fall back to an unanchored explanation.
- Never leave a permanent overlay or retry loop.

Provider/demo failure:

- Preserve the pre-recorded/locally defined canonical demonstration.
- Label live and scripted behavior honestly.


22. LANDING-PAGE CONNECTION

The landing page and app onboarding tell the same story.

Landing page:

- establishes the category POV;
- immediately shows the canonical demo/video;
- explains the old workflow concretely;
- shows the differentiated loop;
- reduces switching anxiety;
- asks for early access or one real workroom.

App onboarding:

- replays or resumes that proof inside the real product;
- lets the user make the human decision;
- applies the first half of the loop to their real work;
- continues into the real result.

The landing video must not be independently invented. Record it from the polished real onboarding/product scenario so claims and visuals cannot drift.


23. MEASUREMENT

Category-comprehension measure:

    After five minutes, how does the user explain Convyio?

Funnel events:

- demo started/completed/skipped;
- onboarding started/paused/skipped/completed;
- real-work versus example path;
- PlanCard produced;
- meaningful constraint added or confirmed;
- Plan accepted;
- bounded Ticket approved;
- ResultCard shown/opened;
- evidence opened;
- project/folder connected;
- local agent paired;
- teammate invited;
- second human contributes before execution.

Activation hypotheses:

- Product activation: accepted Plan after a meaningful constraint.
- Differentiated activation: completed bounded work plus ResultCard/evidence viewed.
- Collaborative activation: a second human contributes before execution.
- Expansion activation: a real project or independently owned agent joins.

Do not use tour completion or first noodle reply as the north-star activation metric.


24. USER RESEARCH

Recruit the narrow ICP:

- 2–10 person technical teams;
- multiple agent users;
- same product/repository;
- recurring deadlines;
- recent concrete coordination failure.

Observe first use and ask users to retell what happened.

Look for:

- whether the old-workflow contrast feels true;
- whether the PlanCard feels useful or bureaucratic;
- whether the constraint-change moment creates the aha;
- whether the user understands the approval as meaningful authority;
- whether ResultCard feels like a practical output;
- whether they still call it Slack with bots;
- whether they would start one real workroom without moving their whole team.

Do not ask only whether they like the interface or concept.


25. ACCESSIBILITY AND DESIGN

Follow AGENTS/DESIGN.md.

- Calm canvas, warm signal.
- One amber accent.
- No gradients.
- Elevated utility for floating surfaces.
- No same-color tinted-border/tinted-background AI boxes.
- Both themes designed independently.
- Visible keyboard focus.
- Native semantic controls.
- Reduced motion.
- No forced timers.
- No autoplay audio.
- Captions/transcript for demo video.
- Narrow viewport and 200% zoom support.
- Personality through noodle's voice and brief moments, not decorated chrome.


26. ACCEPTANCE CRITERIA

The onboarding is complete when:

- a new ICP user sees the category-reset demo first but can skip immediately;
- the landing page and product tell the same story;
- the demo shows the full thread from context to evidence;
- the user makes the consequential human decision in the app version;
- a real-work path produces an inline PlanCard;
- the user adds or confirms a meaningful constraint;
- the Plan visibly changes before execution when information changes;
- Board is explained and implemented as a projection of canonical work;
- bounded work exposes owner, resource, allowed change and verification in human language;
- progress remains in the origin thread;
- ResultCard presents the coherent practical output;
- raw traces remain secondary evidence;
- solo users can complete the core experience;
- invites and integrations remain optional;
- current behavior is never described as an autonomous swarm;
- offline, slow and missing-target states recover cleanly;
- the experience works with keyboard, reduced motion, narrow screens, zoom and both themes;
- instrumentation measures comprehension and differentiated activation;
- observed ICP users accurately explain Convyio after five minutes.
